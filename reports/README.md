## 수동 검증 방법

아래 절차는 사람이 수행할 확인 항목입니다. 이 보고서를 생성했다고 수동 검증까지 완료된 것은 아닙니다. 보고서에 기록된 URL과 점검 권한이 있는 자산을 기준으로 확인하세요.

### 1. 공개 API 접근 여부

1. 보고서의 API 후보 URL을 로그인되지 않은 별도 브라우저 프로필에서 열고 개발자 도구의 Network 탭을 확인합니다. 요청에 Cookie나 Authorization이 없는지 확인합니다.
2. HTTP 상태, Content-Type, 실제 응답 구조를 확인합니다. 200이어도 로그인 HTML이나 공통 화면이면 API 접근이 확인된 것이 아닙니다.
3. JSON 또는 API 명세가 보이면 서비스 담당자에게 의도된 공개 범위를 확인합니다. 명세 공개와 개인정보·내부 데이터의 비인가 공개를 구분합니다.
4. 인증 정책상 제한되어야 하는 데이터가 익명 요청에 반환되는지 담당자와 확인하고, 해당 요청 시각의 서버 접근 로그를 대조합니다. 401/403은 해당 요청의 차단만 의미합니다.

Windows PowerShell에서 헤더만 화면에 확인하는 예시입니다. URL은 보고서의 점검 대상 URL로 바꾸세요. 본문은 저장하지 않고 리다이렉트도 따라가지 않습니다.

```powershell
curl.exe --silent --show-error --max-time 10 --dump-header - --output NUL "https://example.com/api"
```

헤더에도 쿠키 등이 포함될 수 있으므로 공유할 증거에서는 값을 마스킹하세요. 본문 구조는 앞의 브라우저 절차로 확인합니다.

### 2. API 키·토큰 노출 의심

1. 키 패턴이 보고된 페이지·JavaScript·API 응답을 개발자 도구에서 확인하고 apiKey, api_key, secret_key, access_token, client_secret 등의 할당 위치를 찾습니다.
2. 예제 문자열, 환경변수 참조, 공개용 클라이언트 키인지 담당자와 확인합니다. 패턴 탐지만으로 유효한 비밀 키라고 판단하지 않습니다.
3. 소유자의 관리 콘솔에서 키 종류, 활성 상태, 권한, 출처/IP 제한, 사용 이력을 확인합니다. 발견한 키를 요청에 넣어 유효성을 시험하지 않습니다.
4. 비밀 키가 공개된 것으로 확인되면 담당자가 폐기·교체하고 배포 파일과 캐시에서 제거한 뒤 재점검합니다. 키 원문 대신 파일 경로·줄 번호·마스킹된 증거를 기록합니다.

### 3. DB 샘플과 실제 데이터의 연관성

1. 보고서의 일치 필드명을 내부 DB 스키마 및 API 응답 스키마와 대조합니다. 같은 이름이어도 타입·중첩 위치·의미가 다를 수 있습니다.
2. 담당자가 내부 환경에서 마스킹된 샘플의 구조와 시점 정보를 확인합니다. 필드명 일치는 같은 데이터나 같은 유출 사건이라는 증거가 아닙니다.
3. 의심 시간대의 API 접근, DB 조회, 관리자 내보내기, 백업·저장소 다운로드 로그를 대조해 경로와 시점을 확인합니다.

### 4. CVE 후보 적용 여부

1. 보고서의 NVD 출처와 제조사 보안 공지를 확인하고 영향 제품·버전 범위·필수 기능 또는 설정 조건을 정리합니다.
2. 자산 담당자가 배포 목록이나 패키지 정보에서 실제 제품과 버전, 패치 및 백포트 적용 여부를 확인합니다. 공개 서버 배너만으로 판단하지 않습니다.
3. 영향 조건을 모두 만족하는지 확인하여 적용 가능·비해당·정보 부족으로 기록합니다. 적용 가능한 CVE여도 실제 유출 원인은 별도의 사건 로그로 확인해야 합니다.

### 5. 검증 기록

요청 실패·429·미점검·응답 잘림은 검증 완료가 아닙니다. 담당자와 재점검 범위를 정하고 미확인 상태를 유지하세요.

| 항목 / URL | 검증 시각(UTC) | 담당자 | 상태 | 근거 및 조치 |
| --- | --- | --- | --- | --- |
| 공개 API | 미기록 | 미지정 | 미검증 | 익명 응답과 공개 정책 확인 |
| 키 노출 의심 | 미기록 | 미지정 | 미검증 | 키 원문 없이 종류·권한·공개 의도 기록 |
| DB 연관성 | 미기록 | 미지정 | 미검증 | 스키마 및 사건 로그 대조 |
| CVE 후보 | 미기록 | 미지정 | 미검증 | 실제 버전·패치·영향 조건 대조 |

검증 후 상태를 확인됨·오탐/비해당·추가 확인 필요로 갱신하고 근거를 남기세요. 스캐너를 같은 출력 경로로 재실행하면 수동 기록도 덮어쓰므로 작성본은 별도 이름으로 보관하세요.


## 후속 확인 절차 및 한계

1. 내부 DB 스키마와 샘플의 필드 구조를 대조해 데이터 소유 관계를 확인합니다.
2. 의심 시점의 웹/API, DB, 백업 및 클라우드 접근 로그를 대조합니다.
3. 식별한 제품의 정확한 버전과 CPE를 확보하고 CVE 영향 조건을 확인합니다.
4. 확인된 접근 기록과 변경 이력을 근거로 실제 유출 경로를 판단합니다.

이 보고서는 전체 자산 탐색이나 취약점 재현 결과가 아닙니다. CVE 조회는 기술별 최대 10개 후보이며, 조회 실패나 후보 없음은 안전함을 의미하지 않습니다.
